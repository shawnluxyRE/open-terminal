## 开发顺序与并行条件

1. 先固定 HEAD 加 R2 v1.4 工作区快照、407项用例集合及构建基线。T-007 可与 T-008/T-009 并行；保留同步入口的错误契约，避免复制另一套身份或准备逻辑。
2. T-008 与 T-009 共用 `user_isolation.py`，可以并行审查/准备测试，但由 R4 协调修改和集成。先验证短事务、持久预留和最新清单合并，再据同一版本证明集成缓存；不得维护两套归属或持久性确认机制。
3. 集成同时覆盖后台接入、跨用户独立进展、缓存失效。只完成线程转移不能解决长全局锁；只做缓存也不能解决首次准备对事件循环的阻塞。T-010 的完整验证在三项集成后进行，必要局部回归可随任务运行。
4. 原 R5-001 六项回归和新增三状态跨用户持久性用例为硬门槛：B 的新版本可见但目录 fsync 失败时，A 旧缓存必须失配，持续故障不得成功；解除故障先确认版本再使用，之后无需等待 B 的慢 OS 准备。
5. 必要持久化屏障允许等待或明确失败；跨用户性能目标不授权跳过它。每用户锁/全局锁共享等待预算、缓存观察和当前服务线程访问均按 v1.4 完成，不以 TTL、全局禁用缓存或降低断言替代。
6. 完整独立容器回归后验证标准运行镜像与既有 WebUI 连接；复用可用的 A/B、聊天和标记，避免把本轮回归误写成新的首次初始化验收。环境不足只阻止相应验证，不能以旧通过结论代替本轮结果。

### 性能、并发及补充验证

同机、相同镜像依赖、相同用户数据规模与负载，对比三组：改造前旧缓存路径、`59eac68`、本轮新实现。R3 已核对 `7dab0d6` 的旧 `resolve_user` 含内存缓存，可供 R4 固定为旧路径参考；仅在隔离实验中衡量暖访问成本，不能用其旧归属语义替代现行契约或作为部署回退。记录各组实际 revision、调用入口、预热/采样方法及环境差异；旧路径无同版持久清单时注明差异，不伪称状态完全相同。

记录100次暖访问的 p50/p95、外部工作次数和慢 B 存在时 A 的独立进展。R2 当前 p50=2.639ms、p95=3.927ms，清单 open/load 各100次、目录 fsync 100次、passwd全扫200次、group全扫100次、特权命令100次，只是带观测开销的慢路径基线。新实现目标接近旧缓存路径，硬门槛为四类重复重操作归零及不等待其他用户慢 OS；不能将分位数当作跨机器 SLA。5秒仅是并发等待/watchdog 防挂死上限，成功须发生在放闸之前；环境异常单列复核，不放宽该断言。

在现有用例之外，R4 按实现补充以下针对性证据，避免仅凭407项通过推定全部 v1.4 契约已验证：

- 异步取消不提前释放工作线程持锁，线程池有界；同用户等待无半成品发布。
- 分层锁共享30秒等待预算、顺序无反向等待；fork 时其他线程持有的内存锁不会导致子进程死锁，子进程重新建立版本证明。
- NSS 别名/来源变化、跨进程新清单版本、观察期间版本变化可靠失效；不得把新 stat 版本贴到旧核验结果，缓存互斥不包 I/O 或嵌套磁盘锁。
- 非 root 服务的不同工作线程/进程均能实际访问已准备 home；标准镜像 `files systemd` 的账号来源和观察依据可核验，无法可靠观察的额外后端保守回退并单列性能，不把整个标准镜像退回慢路径。
- 原六条 AC 继续有回归支撑：完整身份与 key、稳定空间、随机避碰、并发唯一归属、两池范围/占号、错误脱敏、成功协议与正常 PTY；共用恢复契约和原用户文件不退化。
