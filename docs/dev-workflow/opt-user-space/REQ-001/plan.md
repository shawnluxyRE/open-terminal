本计划只覆盖 REQ-001：可信身份进入产品资源接口，完整 ID 唯一绑定工作账号、私有主组与 home，编号分配、并发首次准备、失败重试及相关恢复。沿用 R2 v1.2 的首次重名随机换名与持久绑定，不再采用历史版本的首次重名直接拒绝策略。接口与算法细节以设计和契约注释为准。

AC-023、AC-034 在本计划中覆盖共用准备模块的重试、现存账号复用和保留 home 的账号恢复契约；真实保留卷重建、服务器重启、兼容升级及完整持久性仍由 REQ-007 验收，个人包可用性另依赖 REQ-005。本次不扩展到 REQ-002 的全面路径/符号链接授权、个人依赖初始化、用户配额、历史迁移或账号删除同步。Notebook 保留并关闭；不修改 Open WebUI，不增加对抗任意用户代码的安全边界。

## 开发顺序与并行条件

1. 开始时核对实际 HEAD、工作区和 R2 v1.2 材料。身份入口、候选名/编号纯规则可先落地；T-001、T-002 与 T-004 的接口接线可按固定契约并行。此阶段的局部测试不能替代最终真实调用链。
2. T-002 先形成“持久预留→资源就绪→重复核验”的完整交付，再完成 T-003 的恢复和异常闭环。两者都修改 `user_isolation.py`，应由 R4 统一安排修改和集成；不得维护两套归属规则。T-001 与 T-004 共同修改 `dependencies.py`，HTTP 与 WS 接线也共享 `main.py`，须协调提交边界。
3. T-004 最终集成 T-001～T-003；既有 `resolve_user` 的元组返回和 `UserFS`/执行器签名保持兼容，旧的“同名即复用”与缓存绕过归属/权限检查路径不得继续参与决定。任务/终端列表与控制不能为统一校验而引入准备副作用；文件列表等文件入口及端口入口仍按设计准备所需账号。`/system` 等元数据不能统一强加用户头。
4. T-005 的场景准备可提前，完整回归在集成后运行；先验证独立 Docker 内的真实 NSS/home，再验证标准镜像中非 root 服务进程的实际访问，随后进行 T-006 的真实 WebUI 联调。任务/终端正常收发与拒绝路径都要覆盖。
5. 只有实现、回归与真实联调结果能共同支撑本需求交付结论。若环境或账号不足，记录受影响 AC 和恢复条件，可继续独立验证，但不得把缺少的证据标记通过。若发现设计或测试契约需改变，先按原编号记录并交回 R2；规划调整记录交 R3，范围或验收变化交用户决定。
